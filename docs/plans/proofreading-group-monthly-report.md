# Групповой месячный отчёт корректуры

Status: draft
Last reviewed: 2026-10-30

## Sources

- Запрос пользователя от 2026-10-28: подготовить развитие индивидуального навыка месячного отчёта до анализа всей корректорской группы.
- Канонический навык: `.agents/skills/onliner-monthly-report/SKILL.md`.
- Подробные правила: `.agents/skills/onliner-monthly-report/references/monthly-analysis.md`.
- Текущий сборщик: `src/actions/tools/crawler.js`.
- Локальный интерфейс проверки: `tools/ledger/index.html`.

## Objective

Поддержать один месячный вход по всей корректорской группе и получить проверяемые индивидуальные расчёты плюс групповой итог без потери авторства, двойного учёта общих материалов и смешивания подтверждённых, кандидатных и ручных начислений.

## Scope

- Описать групповой входной контракт и устойчивую идентичность корректора.
- Отделить общие правила классификации от персональных ставок, секций, графиков, дежурств и исключений.
- Сохранить доказательства на уровне `корректор + материал + ревизия`.
- Определить групповой JSON-контракт, индивидуальные итоги и сводный итог.
- Подготовить сборщик, Ledger и проверки к нескольким корректорам.
- Сохранить совместимость с действующим индивидуальным `onliner.monthly.ledger.v3` на период миграции.

## Non-goals

- Не менять сейчас действующие ставки и правила начисления конкретному корректору.
- Не считать зарплату всей группы из текущих однопользовательских CSV.
- Не считать автора публикации эквивалентом корректора.
- Не публиковать персональные отчёты, административные ссылки или зарплатные данные.
- Не превращать Ledger в источник классификации: канонический анализ остаётся в JSON.

## Current milestone

Согласовать входной формат и правила атрибуции для нескольких корректоров на одном материале, затем зафиксировать минимальный групповой JSON-контракт и набор обезличенных фикстур.

## Dependencies and decisions needed

- Источник состава группы вынесен в `src/actions/proofread-roster.js`: явный roster содержит устойчивый ключ, отображаемое имя и известные Telegram/WordPress-алиасы. Имя само по себе недостаточно устойчиво.
- Источник ревизий: групповой экспорт должен сохранять всех релевантных авторов ревизий, а не только текущего пользователя.
- Общий материал: нужно решить, допускается ли начисление нескольким корректорам и по какому доказательству выбирается основной исполнитель.
- Персональная политика: для каждого участника нужны ставки, регулярные секции, график, duty/SMM/sport-правила и месячные исключения.
- Граница приватности: определить, кто видит индивидуальные суммы и какие поля допустимы в групповой сводке.
- Миграция схемы: предпочтителен групповой контейнер новой версии с независимыми per-member ledgers; плоское суммирование строк v3 неприемлемо.
- Нужны обезличенные примеры минимум для: одного исполнителя, совместной работы, алиаса имени, передачи материала, старой ревизии и спорной атрибуции.

## Acceptance criteria

- Каждый денежный event принадлежит ровно одному участнику или явно помечен как общий нераспределённый event.
- Один материал может быть доказательством для нескольких участников только по явному правилу; это не создаёт скрытого двойного начисления.
- Групповой confirmed total равен сумме индивидуальных confirmed totals, а candidate/manual остаются отдельными.
- Индивидуальный вход продолжает давать эквивалентный ledger v3 в период миграции.
- Все ставки и месячные исключения имеют источник и область действия.
- Ledger не классифицирует и не пересчитывает зарплатную семантику из эвристик интерфейса.
- Персональные данные и admin-ссылки не попадают в публичную сборку.

- 2026-10-30 — `cms.sections` служит единым источником подписей, Fluent Emoji и нативных маркеров разделов для crawler и Ledger. Автономная сборка Ledger получает словарь через свой bundled-модуль, не создавая отдельную таблицу представления.

Верхняя граница намеренно отсутствует: последующая передача другому корректору относится к истории записи, а правки до отчётного периода не влияют на сигнал.

- 2026-10-28 — не создавать пустой discoverable skill для группы: до согласования входа он мог бы ошибочно активироваться и выдавать недостоверные расчёты.

- 2026-10-28 — не использовать поле автора публикации как идентичность корректора; основанием служат ревизии и явный roster/alias mapping.
- 2026-10-29 — raw crawler v2 не адаптируется к ledger v3: зарплатные строки, расчётные payroll-сигналы и итоги появляются только из заранее рассчитанного индивидуального ledger. Raw-просмотр может показывать исходные редакционные признаки и консервативные evidence-сигналы, но не трактует их как начисления.
- 2026-10-29 — предыдущая чужая ревизия считается лишь приблизительной точкой передачи, а не официальным `submitted_at`; порог дедлайна без отдельного правила не выдумывается.
