# AD-002 Audit Evaluation Observations

Status: experimental

## Problem

Prompt quality must be evaluated on real editorial work, not only on invented
examples. At the same time, one admin interaction contains several different
layers of behavior:

- the model generates a result;
- runtime normalization and filters decide what is usable;
- the audit UI decides what is shown;
- an editor accepts, changes, dismisses, or leaves a suggestion unresolved;
- a later reviewer may decide whether the suggestion was actually correct.

If these layers are collapsed into one metric, the result is misleading. For
example, an accepted suggestion is useful behavioral evidence, but it is not
automatically ground truth. A suggestion removed by a deterministic runtime
filter is also not the same failure as a suggestion dismissed by an editor.

## Decision

Start with an audit-only observation experiment. Do not generalize it into a
cross-product analytics framework yet.

The audit flow is the first useful boundary because it already has:

- a real model invocation;
- normalized and filtered suggestions;
- an explicit review UI;
- accept, dismiss, manual override, and undo actions;
- an existing developer download path.

The implementation records one final snapshot of this flow and lets the editor
save it locally. The snapshot is intended for offline prompt evaluation, not
for product telemetry or user monitoring.

## Current data flow

```text
src/prompts/editorial.js
        task id / revision / compiled prompt
                        |
                        v
src/core/llm.js         provider execution
                        |
                        v
src/actions/audit.js    generated -> filtered -> presented -> editor decision
                        |
                        v
.eval/inbox/*.json      ignored local raw observations
                        |
                        v
evals/run.js            aggregate observation reports
                        |
                        v
human review            redact, label, and select representative cases
                        |
                        v
evals/editorial/        committed task-specific regression suites
```

Saving is explicit. The browser keeps the observation in memory during the
audit session, but does not silently write or upload editorial content. When
the File System Access API is available, the editor can choose
`.eval/inbox/`; otherwise the browser uses its normal download behavior.

## Evaluation layers

The following layers must remain distinguishable:

| Layer | What it tells us | What it does not prove |
| --- | --- | --- |
| generation | what the provider/model returned | that the result reached the editor |
| normalization and runtime filtering | what the application could parse and retained | that a filtered item was a model-quality failure |
| presentation | what was actually visible in the audit UI | that the editor evaluated every visible item |
| interaction | accepted, dismissed, customized, undone, or pending | objective correctness |
| curated eval | reviewer-approved expected behavior and labels | live product adoption by itself |

Prompt precision/recall or correctness scores require a curated expected
result. Interaction data alone supports operational metrics such as acceptance,
customization, dismissal, resolution, latency, and token usage.

## Observation contract

The current snapshot schema is `onliner.prompt-eval-observation/v1`. It keeps:

- capture time and source page identity;
- task id and revision;
- exact compiled prompt and prompt hash;
- provider and model;
- start/end timestamps, latency, and available token usage;
- source text and source key;
- normalized model output;
- generated suggestions;
- suggestions that survived runtime filters and were presented;
- editor decisions and the final text;
- raw provider responses for debugging.

The aggregation key is currently:

```text
task id + revision + prompt hash + provider + model
```

This prevents reports from silently combining different prompt revisions or
model configurations.

## Interpretation rules

- `accepted` means the editor applied a suggestion; it is a usefulness signal,
  not verified correctness.
- `customized` means the editor applied a changed replacement; it is evidence
  that the suggestion direction may have helped but its proposed edit was not
  sufficient as-is.
- `dismissed` means the editor explicitly rejected or skipped a suggestion.
- `pending` means no decision was observed and must not be counted as rejection.
- `runtimeFiltered` belongs to the application pipeline, not the UI decision
  layer.
- undo removes the corresponding final decision so the snapshot represents the
  resulting audit state.
- slug and excerpt are generated by the current composite request, but the
  audit UI does not yet record an equivalent accept/reject lifecycle for them.

## Data ownership and privacy

- Raw observations stay under ignored `.eval/` storage.
- Raw snapshots may contain full article text, page URLs, and provider output;
  they must not be committed by default.
- Only minimal, reviewed, and redacted cases should be promoted into
  `evals/editorial/`.
- Production prompt modules do not own eval data.
- Shared runner/report code lives in `evals/`; task-specific suites live below
  that boundary rather than next to production features.
- No automatic upload, user identity tracking, or remote analytics endpoint is
  part of this experiment.

## Known limitations

- Capture is implemented only in `audit`.
- Persistence requires an explicit save/download action.
- Only decisions made through the audit review controls are observable.
- The current model request is composite: audit edits, slug, and excerpt share
  one invocation, while detailed interaction feedback currently covers audit
  edits only.
- Acceptance can be affected by time pressure, convenience, or editor style.
- A final snapshot is not an append-only event history.
- The current data cannot attribute causality between individual prompt
  sections and individual outputs.
- Cross-task and cross-session analysis is deliberately out of scope.

## Validation plan for this experiment

1. Collect real audit snapshots from ordinary admin work.
2. Check whether generated, presented, decision, undo, and manual-override
   states match what actually happened in the UI.
3. Aggregate observations without treating pending items as failures.
4. Review repeated accepted, customized, dismissed, and filtered patterns.
5. Promote a small redacted representative set into task-specific regression
   suites.
6. Compare prompt revisions on the same curated cases and compatible model
   configuration.
7. Record findings that cannot be represented by the current schema before
   expanding the instrumentation.

## Conditions for generalization

Extract a shared observation/instrumentation layer only after the audit
experiment is validated and at least one additional task needs the same
lifecycle. The next design should then decide:

- a shared observation envelope versus task-specific payloads;
- stable observation, source, prompt, result, and event identifiers;
- explicit stages such as generated, normalized, filtered, presented,
  selected, applied, edited, dismissed, and undone;
- atomic versus composite-task attribution;
- capture for slug, excerpt, headline, lead, and future tasks;
- final snapshots versus an append-only event log;
- sampling, redaction, retention, and export policy;
- whether instrumentation belongs in each integration action or behind a
  shared runtime boundary;
- how reports separate prompt quality, provider behavior, application filters,
  UI usability, and editor preference.

## Rejected alternatives for now

- A universal analytics framework before real audit data exists: premature and
  likely to encode the wrong lifecycle.
- Synthetic examples as the production eval corpus: useful only for runner
  self-checks, not prompt-quality claims.
- Keeping eval data beside prompts or action code: mixes production semantics
  with evidence and test data.
- Silent upload or automatic server persistence: unnecessary for the current
  experiment and unsafe for editorial content.
- Treating acceptance rate as a correctness score: conflates behavior with
  reviewed quality.
